# Astra 第一版设计

## 1. 目标与范围

在一周以内实现可进入平台联调和提交准备的《未来战争》参赛程序。用户确认：队名 Astra；优先赢比赛和最终排名；模型由平台提供，不训练或更换；平台支持 C/C++/Go/Rust/Python；目前没有额外判题器、测试平台或运行环境资料。

主程序选择 C++，以 C++17 为实现标准目标；任务沙盒执行 Python 脚本。架构选择见 ../../adr/0001-cpp-core-and-python-task-scripts.md。语言可用不代表具体编译标准、系统架构与打包约定已经确认。

第一版实现稳定的协议服务、经济与防守基线、任务执行和配方复用、新闻与宝藏线索管理，并为候选战术提供可重复的评测。规则推演用于挑选实验，不作为已证明的胜率结论。没有官方环境时，可交付本地可运行版本；正式平台兼容性和比赛有效性必须留待联调确认。

不开展模型训练、外部模型接入、通用多代理平台或完整强化学习项目。每项功能都需对应动作合法性、任务收益、生存或对战评测。

## 2. 规则依据与不确定性

主要来源：

- [任务书](https://github.com/Tymonxiong/Competition/blob/main/docs/任务书.md)
- [接口文档](https://github.com/Tymonxiong/Competition/blob/main/docs/接口文档.md)
- [官方 Demo](https://github.com/Tymonxiong/Competition/tree/main/Demo)

公开资料核查日期：2026-09-14。Demo 和请求/响应样例用于理解接口；样例存在缺失字段和动作目录式重复键，不能原样作为完整有效的判题输入或输出。

明确规则包括：41×32 地图、八方向移动、切比雪夫距离；一天 70 白天回合和 60 夜晚回合；最多 1300 回合；两工人和一开拓者；三座武器总上限；每角色每回合至多一个动作；武器需邻接角色操控。当前矿价由 vendorShopList 提供。敌方没有公开 totalScore 字段；其基地和墙全图可见，其他单位受视野限制，机器人全图可见。

每个游戏日通常最多三次 LLM 调用；执行自进化任务期间不计入该限额。LLM 和命令结果在后续请求中以“上回合结果”提供。任务沙盒不能访问外网，单条命令最多 15 秒，输出最多 64KB。HTTP 收到请求后 5 秒内需响应，累计五次规定异常会停止调度，退出不重启。

以下信息缺失或有歧义，集中管理为规则假设，不分散硬编码：

| 编号 | 未确认条件 | 会影响的功能 | 未确认时的处理 |
|---|---|---|---|
| R1 | 正式建造区坐标、地图配置 | 合法布防与共同操炮站位 | 场景显式提供建造区；真实地图配置注明来源，图示推定不算平台验证 |
| R2 | 火箭冷却递减时序、换塔是否有额外代价 | 单人三炮、伤害预测 | 在线以观测 cooldown 为准；模拟比较候选时序；轮换为可关闭战术 |
| R3 | 火箭空格溅射、敌建筑伤害、基地多格结算 | 落点搜索与远程攻城 | 默认只对可见机器人坐标选择落点，不启用远程攻城 |
| R4 | 机器人目标、移动与攻击顺序、墙的作用 | 威胁预测、布墙 | 简单规则基线配合多种候选模型，记录预测误差；不宣称模拟等同判题 |

| R6 | 任务反馈、最早完成时序、沙盒持久性、真实题目 | 速度优化、配方晋级 | 等待实际命令结果后提交；脚本可重建；不依赖逐字段评分 |
| R7 | 单方存活及其他未覆盖组合的最终判胜细则 | 胜负模拟 | 将未确认结果标记为未决，保留双方原始指标，不编造胜率 |
| R8 | 编译器、CPU/内存、模型长度与延迟、提交规范 | 性能与打包 | 搜索预算可调；控制提示长度；提供启动入口但以平台说明完成最终验证 |

## 3. 主程序结构

一个参赛进程接收 HTTP POST JSON，返回 JSON。启动入口遵循文档形式 bash run.sh port，服务监听 0.0.0.0。LLM 和任务脚本由判题器执行；HTTP 请求线程只生成下一步请求，不等待它们完成。

核心接口按职责划分：

| 组件 | 输入 | 输出与职责 |
|---|---|---|
| 协议适配 | 原始请求 JSON | TurnObservation；保留缺失与未知状态，不将未知坐标变成 (0,0) |
| 局内状态 | 本轮观测、上一轮动作与结果 | MatchMemory；新闻原文、任务上下文、库存计划、预测误差 |
| 战略协调 | 观测、记忆、候选方案 | 各角色目标、金币和物品预算、任务时间预算 |
| 经济与导航 | 角色目标、地图占用与资源 | 移动、采集、交易、建造、升级、修复候选 |
| 战斗分配 | 武器、可用操作者、机器人、冷却 | 合法武器与操作者配对及联合攻击候选 |
| 任务执行 | phaseTask、llmResp、lastCmdResult | prompt、executeCmd、开拓者候选动作、配方状态 |
| 输出裁决 | 角色动作、模型与命令候选、共享资源 | 最终 roleCommandMap、至多一个 prompt、至多一个 executeCmd |
| 预算与降级 | 单调时钟、已生成可行动作 | 搜索截止时输出已有方案；异常模块不拖垮其他模块 |

线上决策与离线评测共享协议、几何、动作检查和战术代码。机器人模拟为独立可替换组件，以免将推测的机器人行为变成协议事实。初始实现使用显式规则配置，不建设插件框架。

### 3.1 每回合决策顺序

1. 解析请求，确认阵营、角色、回合、地图、可见状态和上回合反馈。
2. 检查对局边界并更新记忆；缺失必需观测时输出保守空指令，记录原因。
3. 按上一轮实际发送的请求关联 LLM/命令结果，避免把旧任务结果交给新任务。
4. 计算近期威胁、可安全使用的人手、库存、可接任务和昼夜剩余回合。
5. 先生成能在有限时间内完成的规则基线；再用剩余预算搜索战斗与调度改进。
6. 合并经济、战斗和任务候选。为角色、武器、站位、金币和物品做统一分配。
7. 完成最终检查和 JSON 序列化；记录本轮真正发送的动作，及时返回。

默认候选搜索预算先设为 100ms，可配置；这是工程初值，不是已测性能。总响应预算留足解析和序列化时间，任何搜索都必须周期性检查单调时钟。以整条服务请求的延迟作为验收指标。

### 3.2 记忆边界

以 teamId、阵营和回合演进识别局内上下文。回合倒退、阵营变化或明确的新局信号触发重置；同回合重复请求只有在有效输入完全一致时才复用先前响应，输入不同则报告冲突并保守处理，避免状态重复推进。具体半场重启行为留待平台验证。

局内保存每条新闻原文与日期、已观察敌方信息及时间、每个任务的本地序号、上一轮请求、已验证字段及配方证据。过期敌方观测不是当前可见事实。不假定两半场或不同比赛共享沙盒文件、内存或已探索知识。

### 3.3 动作裁决

attack 的映射键为被操控武器 ID，controllerId 为角色 ID。检查武器和操作者存活、距离、夜晚、冷却、目标数及锥形限制，并占用操作者当回合动作。不能因攻击键是武器 ID 就让该角色同时移动、提交答案或操作第二座武器。

共享金币与背包物品按最终动作合计预留；不能让两个模块分别花同一笔钱。移动方案预留目标格并避免相互交换；真实对手或机器人运动造成的合法失败按反馈调整，不当作协议异常。未知建造区域、未知目标类型或字段缺失不得凭默认值生成进攻性动作。

任务探索与新闻提取共享唯一 prompt 槽位，所有请求候选注明来源、任务序号、预期收益和额度需求，由输出裁决选出至多一项，不允许后写字段覆盖前一个请求。executeCmd 同样只接受一项且必须属于当前确认的任务。先确定角色动作，再检查任务权限：若最终动作离开任务范围、提交可能结束任务的答案，或观测到任务已结束，则不发送依赖该任务继续存在的命令；不能依赖同回合 acceptTask 立刻获得权限。模型额度统一按实际发送次数记录，状态不确定时使用普通日额度；无法支付额度就不发送。只为最终发出的 prompt/命令建立 pending 关联。

## 4. 胜率导向的战略

短期先满足基地和操作者的安全约束，再分配剩余人手与资金给任务、宝藏、经济和进攻。约束是可随时间和观测调整的安全余量，不是“永远防守优先”。在已验证生存余量充足时，将更多资源投入任务；危机时及时停止长途计划。

战略比较近期存活风险、任务成功概率及回合数、金币收入与下一次升级价值。没有敌方总积分时，只维护对手能力和可能收益的范围，不以不可观察的精确分差切换策略。第一版先使用可解释规则和有限候选搜索，权重通过对照场景确定。

### 4.1 经济与导航

使用实际 vendorShopList 价格选择采矿与批量出售；新闻只辅助预测未来可采性和价格变化。矿路评价包含往返距离、采集回合、出售动作、容量和回防时间。建造、采购与任务出发都检查完成后是否还有安全返回路径。

八方向路径规划考虑 2×2 基地占地、矿区、中立单位、任务点、建筑、机器人与已知角色占用。对角移动按规则允许从相邻障碍间通过；多角色联合规划避免目标争抢和位置互换。角色死亡后等待实际观测到复活，不靠计时器凭空恢复角色。

### 4.2 战斗与操炮轮换

三座武器的类型组合共十种；用相同场景和双方位置比较，不预先认定三火箭最优。计算攻击时联合考虑击杀、溅射、过量伤害、射程、冷却、威胁紧迫性和操作员占用。电磁炮的能量会因已造成伤害耗尽，不能把穿透当作对每个目标造成满额伤害。

若合法布局存在三座火箭炮邻接范围的共同可站格，且实际反馈支持无额外代价换炮，评估 A/B/C/空 的轮换。在三个完整冷却空窗的假设下，60 回合可发射 45 次，与三个固定操作者的发射次数相同，但齐射时机与受击风险不同。有限射程、非群聚敌人、昂贵升级和共同站位的脆弱性都进入对比。

另一工人是否离开防线、开拓者能否夜间留在任务点，由实际威胁决定。没有安全站位时恢复多角色操炮基线。三座武器全部从一级升到三级需额外 750 金币，不能把三级火箭能力当作开局可用。

### 4.3 升级、围墙和补给

基地升级回满血，可以作为两次有限恢复机会。1500→3000→4500 的理论累计承伤接近 9000 需要理想时机，不作为实际安全保证。提前买券、安排邻接角色，以未来伤害上界和结算不确定性决定触发点，缺少可靠预测时提前使用。

围墙按实际延迟和承伤价值评估；禁止把“机器人一定绕迷宫”写为确定规则。修复需要角色可到达，封墙前检查任务路线和操炮站位。武器覆盖重建会损失原有武器与等级，必须作为明确成本。

### 4.4 进攻

从目标阵营机器人的血量和位置变化、敌方基地与墙的损伤估计防守能力，保留区间和观测来源。不要把机器人消失一律当作击杀，日夜切换会清除残余机器人。

召唤令只在预期增加的压力有机会突破防线、且自身有足够生存余量时购买使用。评估自然浪潮、每晚时长、每日十张上限和赠送对手的击杀收益。未验证武器可伤害敌建筑前，不启用三级火箭全图攻城，也不假设 2×2 基地重复计伤。

## 5. 弱模型任务系统

### 5.1 任务状态与结果关联

状态依次为：空闲、前往任务点、等待接取确认、探索或执行、等待结果、检查与提交、结束。以 phaseTask、任务点状态、角色位置/存活和上回合动作共同判断状态；重复题面也可能是新任务，不能仅凭文本相同判断已做过。

在接取回合 t 后，通常 t+1 才看到题面：输入足够时可直接计算并提交；需要沙盒时 t+1 发命令，t+2 用返回结果提交；未知任务还可能增加探查和模型轮次。领取与命令的准确顺序待验证。绝不在同一个响应中提交依赖尚未返回命令结果的新答案。

只有在观测确认处于任务执行期时使用 executeCmd，并按确认的任务状态管理 LLM 额度。提交可能结束任务时，避免依赖同回合额外的无限额模型调用。沙盒故障和命令超时按文档不计队伍异常，但仍计入任务的时间损失。

### 5.2 三条解题路径

1. 配方与适用条件吻合：程序填参数，一条命令完成必要查询、计算和检查。
2. 配方已知但参数提取不确定：模型在提供的候选和字段中填槽，程序检查后执行。
3. 新任务：先获取足够但有界的实际信息，再要求模型提出下一条可验证操作；执行后用结果纠正或形成配方。

不提前臆造真实题库或为未知 API 建大量适配器。首版提供基础文件观察、文档读取、JSON/文本处理及 Python 执行骨架；专用配方由实际样题、任务说明或观测结果驱动。

### 5.3 模型输出与执行

提示只包含当前相关题面、选定证据、实际工具能力和清晰输出格式。模型输出限制为任务类别、参数、证据出处、操作建议或代码；字段不符先拒绝应用，并在剩余回合值得时发一次针对性修正请求。重复失败切换保守路径，避免整题陷入格式修复。

程序负责数字、日期、字段名和答案格式检查；无法验证的猜测保留为候选。对新任务确需生成代码时，仅通过任务沙盒执行，观察输出后再决定答案；不让生成代码修改参赛决策内核。

脚本优先使用已确认可用的 Python 标准库，内部设置预算，输出精简结果和本地任务/命令序号，避免超过 15 秒或 64KB。序号用于关联，不能代替对返回结果的实际验证。API 和文件路径来自题目与合法环境探查，禁止猜测外网可访问。

### 5.4 解题配方与验证

配方包含：适用任务特征、接口/文件前提、参数提取规则、执行脚本、答案格式、检查规则，以及来源任务和验证证据。主程序保存配方；沙盒文件只当可重建缓存。结构变化时重新验证，不能因为城市名等参数变化就重写整个解法，也不能因为题目相似就忽略接口变化。

区分候选方法、本地检查通过、比赛观测支持三种证据。角色动作合法不等于答案正确；没有 errorCode=2 也不能脱离任务状态单独证明完成。只有明确反馈，或在未超时、角色未离开/死亡的受控条件下观察到与提交一致的任务结束和收益，才能提高比赛验证等级；信息不足时保留不确定标记。

接口没有结构化逐字段通过率。先提交可独立验证的部分答案，仅在题目格式允许时使用；不要虚构未知字段。超时采用历史最高通过率有明确依据，但不把这条规则扩展到主动离开或死亡。将提交的答案及本地证据保留，结束原因不明时不覆盖可靠配方。

### 5.5 新闻与宝藏

保存逐日原文，模型逐条抽取带出处的地点、时间、物品和真假条件，程序统一时间并维护候选约束。首版支持实际样例需要的有限约束类型；遇到不能表达的语义，保留原文并让模型针对该处分析，不装作已完成通用自然语言逻辑求解。

采购与出发计划考虑背包、金额、路径、开启时间和回防。合法失败召唤也消耗物品，物品要求不能多也不能少。结果码“无宝藏或未到时间”不能分解成两个事实；“物品错误”也不能在未知检查顺序下证明地点和时间正确。

## 6. 实验与验收

### 6.1 验证层次

- 协议与单元测试：已明确规则，如坐标、冷却使用、动作归属、预算预留和结果关联。
- 场景与回放：验证多模块实际交互、超时降级、换边和连续多回合状态。
- 自建模拟对照：同一场景/随机种子，交换双方位置，记录存活、游戏分、任务耗时、人手和金币使用；结果注明机器人行为与判胜假设。
- 官方联调：收到真实环境后验证启动、建造区、关键时序、任务格式和实际对战。只有这层能支持正式兼容性及正式胜率结论。

### 6.2 第一版验收

1. 回放或合成输入连续运行 1300 回合；无进程退出，输出可解析，各角色无双重动作或预算超配。
2. 在记录硬件与输入规模的本机测试中响应明显小于 5 秒，搜索触顶仍有合法基线输出；正式性能待平台复测。
3. 路径、基地占地、碰撞预留、昼夜边界、角色死亡和换边均有独立场景。
4. LLM 空响应、无效 JSON、错误参数或旧任务结果不会阻止基本经济与防守。
5. 用明确标记为合成的任务验证：首次探索、后续参数复用、接口变化拒绝误用、沙盒清空可重建、结果下一回合提交。
6. 对战术对照报告实际配置及假设；不将 45 次理论发射或自建模拟胜率写成官方验证。

### 6.3 最先执行的官方小实验

按价值顺序核验：合法建造区与站位；火箭冷却和换塔；敌建筑伤害及空格溅射；机器人目标与墙的作用；升级结算；任务最早提交及反馈；记忆/沙盒重置；未明确的判胜组合。每项独立场景，只变一个关键条件，以原始请求、响应和观测结果为证据。

## 7. 一周交付顺序

| 阶段 | 必须形成的可运行结果 | 可裁剪扩展 |
|---|---|---|
| 第 1 天 | 构建、HTTP、协议、状态、回放与空指令降级 | 日志展示美化 |
| 第 2 天 | 寻路、资源分配、经济和布防规则基线 | 长期价格优化 |
| 第 3 天 | 联合攻击、操作者分配、升级与修复 | 深层搜索、进攻推断 |
| 第 4 天 | 任务状态机、脚本执行、配方复用 | 更多任务族 |
| 第 5 天 | 新闻/宝藏证据管理、任务与防守协调 | 复杂约束推理 |
| 第 6 天 | 可重复对照、失败场景修复、参数选择 | 更多机器人模型 |

若进度受限，优先协议正确、基本生存和任务执行链路；复杂搜索、进攻与广泛题型适配按实测收益取舍。没有真实地图、任务或运行说明的问题记录为外部验证缺口，不以猜测补齐并宣称可正式提交。
